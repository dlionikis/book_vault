# Data Validation & Type Safety Layers

> **TL;DR**: OpenAPI is the single source of truth. Database schema defines storage, TypeScript provides compile-time safety, Zod validates responses in contract tests (not in production routes yet), and iOS consumes the same OpenAPI contract via auto-generated Swift models.

**Last Updated**: December 27, 2025

## Layer-by-Layer Breakdown

### 1. OpenAPI Specification (The Contract)

**File**: `docs/api/openapi.yaml`

**Purpose**: Single source of truth for API contracts

**Defines**:

- Request/response schemas
- Data types and formats
- Required vs optional fields
- Validation rules (min/max, patterns, enums)
- API endpoints and HTTP methods

**Example**:

```yaml
components:
  schemas:
    Book:
      type: object
      required:
        - id
        - title
        - asin
      properties:
        id:
          type: string
          format: uuid
        title:
          type: string
          minLength: 1
        asin:
          type: string
          pattern: '^[A-Z0-9]{10}$'
        runtime_minutes:
          type: integer
          minimum: 0
```

**Why it's the source of truth**:

- Human-readable documentation
- Language-agnostic (generates TypeScript AND Swift)
- CI/CD enforces compliance (contract tests fail if violated)
- Versioned with the codebase

### 2. Auto-Generated TypeScript Types

**File**: `lib/api-types.ts` (DO NOT EDIT MANUALLY)

**Generated by**: `npm run api:generate:ts` (uses openapi-typescript)

**Purpose**: Compile-time type safety for backend API routes

**Example Output**:

```typescript
// Generated from OpenAPI spec
export interface paths {
  '/api/books/{id}': {
    get: {
      parameters: {
        path: { id: string };
      };
      responses: {
        200: {
          content: {
            'application/json': {
              id: string;
              title: string;
              asin: string;
              runtime_minutes?: number;
              // ... all fields from OpenAPI
            };
          };
        };
      };
    };
  };
}
```

**How it's used**:

```typescript
// app/api/books/[id]/route.ts
import { paths } from '@/lib/api-types';

type BookResponse =
  paths['/api/books/{id}']['get']['responses']['200']['content']['application/json'];

export async function GET(request: NextRequest) {
  // TypeScript enforces this matches the OpenAPI spec
  const book: BookResponse = {
    id: '...',
    title: '...',
    asin: '...',
    // Missing required field? TypeScript error!
  };

  return NextResponse.json(book);
}
```

**Regeneration**:

- Automatic: Pre-commit hook when `openapi.yaml` changes
- Manual: `npm run api:generate:ts`
- CI check: Fails if types are stale

### 3. Prisma Schema (Database Layer)

**File**: `prisma/schema.prisma`

**Purpose**: Database schema definition and ORM types

**Defines**:

- Table structure
- Relationships (one-to-many, many-to-many)
- Database constraints (unique, indexes)
- Default values

**Example**:

```prisma
model Book {
  id              String   @id @default(uuid())
  asin            String   @unique
  title           String
  description     String?  @db.Text
  runtimeMinutes  Int?     @map("runtime_minutes")

  authors         BookAuthor[]
  series          BookSeries[]

  @@index([title])
  @@map("books")
}
```

**Key Differences from OpenAPI**:

- **Storage-focused**: Includes DB-specific concerns (indexes, foreign keys)
- **Relationships**: Defines joins between tables (BookAuthor, BookSeries)
- **Naming**: Uses snake_case in DB, camelCase in code via `@map()`

**Generated Types**:

```typescript
// node_modules/.prisma/client/index.d.ts (auto-generated)
import { Prisma } from '@prisma/client';

// Prisma generates types for database models
type Book = {
  id: string;
  asin: string;
  title: string;
  runtimeMinutes: number | null;
  // ...
};
```

### 4. Runtime Validation (Zod) - TESTING ONLY

**File**: `lib/api-schemas.ts`

**Current Status**: ✅ Zod IS installed and used, but ONLY for contract tests

**Purpose**: Runtime validation of API responses in automated tests

**Where it's used**:

- `__tests__/api/api-types-validation.test.ts` - Contract tests that validate actual API responses

**Example schemas**:

```typescript
// lib/api-schemas.ts
import { z } from 'zod';

export const BookSchema = z.object({
  id: z.string().uuid(),
  title: z.string(),
  asin: z.string(),
  runtime_minutes: z.number(),
  cover_url: z.string().url(),
  audio_url: z.string().url(),
  authors: z.array(AuthorSchema),
  // ... more fields
});

export const BooksListResponseSchema = z.object({
  books: z.array(BookSchema),
  pagination: PaginationSchema,
});
```

**How it's used in tests**:

```typescript
// __tests__/api/api-types-validation.test.ts
it('validates /api/books response', async () => {
  const response = await axios.get(`${API_BASE}/api/books`);

  // This throws if validation fails
  const parsed = BooksListResponseSchema.parse(response.data);

  expect(parsed.books).toBeInstanceOf(Array);
});
```

**What it validates**:

- API responses match OpenAPI spec structure
- All required fields are present
- Field types are correct (string, number, uuid, url, etc.)
- Nested objects have proper structure
- Arrays contain valid items

**Why ONLY in tests?**:

- ✅ Catches drift between OpenAPI spec and actual responses
- ✅ Provides detailed error messages when tests fail
- ✅ Validates runtime data (TypeScript only checks compile-time)
- ❌ NOT used in production API routes (no request validation yet)
- ❌ NOT used for user-facing error messages

**Why not in API routes yet?**:

- OpenAPI spec + TypeScript provides compile-time safety
- Contract tests catch implementation drift
- No complex validation logic needed yet (all fields simple types)
- Adding Zod to routes would be future enhancement for better UX

## How They Work Together: Full Request Flow

Let's trace a **GET /api/books/{id}** request through all layers:

### 1. OpenAPI Defines Contract

```yaml
# docs/api/openapi.yaml
paths:
  /api/books/{id}:
    get:
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: string
            format: uuid
      responses:
        200:
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Book'
```

### 2. TypeScript Types Generated

```typescript
// lib/api-types.ts (auto-generated)
type BookResponse =
  paths['/api/books/{id}']['get']['responses']['200']['content']['application/json'];
```

### 3. Backend API Route Implementation

```typescript
// app/api/books/[id]/route.ts
import { paths } from '@/lib/api-types';
import { prisma } from '@/lib/db';

type BookResponse =
  paths['/api/books/{id}']['get']['responses']['200']['content']['application/json'];

export async function GET(request: NextRequest, { params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;

  // 1. Fetch from database (Prisma types)
  const dbBook = await prisma.book.findUnique({
    where: { id },
    include: {
      authors: { include: { author: true } },
      series: { include: { series: true } },
    },
  });

  if (!dbBook) {
    return NextResponse.json({ error: 'Not found' }, { status: 404 });
  }

  // 2. Transform Prisma data to API response shape
  const response: BookResponse = {
    id: dbBook.id,
    title: dbBook.title,
    asin: dbBook.asin,
    runtime_minutes: dbBook.runtimeMinutes,
    authors: dbBook.authors.map((ba) => ({
      name: ba.author.name,
      asin: ba.author.asin,
    })),
    // TypeScript enforces this matches OpenAPI spec!
  };

  // 3. Return JSON (contract test validates this)
  return NextResponse.json(response);
}
```

### 4. Prisma Fetches from Database

```typescript
// Prisma Client (auto-generated from schema.prisma)
const dbBook: {
  id: string
  asin: string
  title: string
  runtimeMinutes: number | null
  authors: {
    author: {
      name: string
      asin: string | null
    }
  }[]
} = await prisma.book.findUnique(...)
```

### 5. PostgreSQL Executes Query

```sql
-- Generated by Prisma
SELECT
  b.id, b.asin, b.title, b.runtime_minutes,
  a.name, a.asin
FROM books b
LEFT JOIN book_authors ba ON b.id = ba.book_id
LEFT JOIN authors a ON ba.author_id = a.id
WHERE b.id = '...';
```

### 6. iOS Client Receives Response

```swift
// iOS app
let book: Book = try await apiClient.getBook(id: bookId)

// Swift model (auto-generated from OpenAPI)
// Matches backend response exactly
print(book.title) // Type-safe access
```

## Validation Happens at Multiple Layers

### Compile-Time Validation (TypeScript)

**What it catches**:

- Missing required fields
- Wrong data types
- Typos in property names

**Example**:

```typescript
const response: BookResponse = {
  id: '123',
  title: 'Book Title',
  // TypeScript error: Property 'asin' is missing!
};
```

### Runtime Validation (Contract Tests)

**What it catches**:

- API responses don't match OpenAPI spec
- Extra/missing fields in actual responses
- Wrong HTTP status codes

**Example**:

```bash
npm run test:contract

# Fails if:
# - Response missing required field
# - Field has wrong type
# - Response doesn't match schema
```

### Database-Level Validation (Prisma + PostgreSQL)

**What it catches**:

- Constraint violations (unique, foreign key)
- Data type mismatches
- NULL values in required fields

**Example**:

```typescript
// This will fail at database level
await prisma.book.create({
  data: {
    asin: 'B0123456789', // Already exists
    title: 'New Book',
  },
});
// Error: Unique constraint violation on 'asin'
```

### iOS Compile-Time Validation (Swift)

**What it catches**:

- Type mismatches when decoding JSON
- Missing required properties
- Wrong property types

**Example**:

```swift
// This won't compile
let book: Book = response
print(book.invalidProperty) // Swift error: no such property
```

## Data Transformation Points

Data changes shape as it flows through the system:

### 1. Database → Prisma (Type Transformation)

```typescript
// Database has snake_case
runtime_minutes INT

// Prisma provides camelCase
runtimeMinutes: number | null
```

### 2. Prisma → API Response (Shape Transformation)

```typescript
// Prisma returns nested relations
{
  id: '...',
  authors: [
    {
      author: { name: 'Author Name', asin: 'B01...' }
    }
  ]
}

// API flattens to match OpenAPI spec
{
  id: '...',
  authors: [
    { name: 'Author Name', asin: 'B01...' }
  ]
}
```

### 3. API → iOS (Same Shape, Different Language)

```typescript
// TypeScript API response
{
  runtime_minutes: 360;
}

// Swift model
runtimeMinutes: Int = 360;
```

## Why This Architecture?

### Benefits

1. **Single Source of Truth**: OpenAPI spec defines the contract
2. **Type Safety Everywhere**: Compile-time errors in TypeScript AND Swift
3. **No Manual Sync**: Types auto-generate from spec
4. **Contract Enforcement**: CI fails if implementation drifts from spec
5. **Documentation**: OpenAPI spec is human-readable docs
6. **Platform Agnostic**: Same spec generates types for web AND mobile

### Trade-offs

**Zod in tests only**:

- ✅ Contract tests validate responses at runtime
- ✅ Detailed error messages when API drift occurs
- ✅ Simpler production stack (no validation overhead)
- ❌ No runtime validation of request bodies in API routes
- ❌ Generic error messages for malformed user requests

**Prisma ≠ OpenAPI Schema**:

- ✅ Database can have more fields than API exposes
- ✅ API can aggregate/transform data
- ❌ Manual transformation layer needed (Prisma → API shape)
- ❌ Two schemas to maintain (but serve different purposes)

## Common Questions

### Q: Why not generate Prisma schema from OpenAPI?

**A**: Different concerns:

- **OpenAPI**: External API contract (what clients see)
- **Prisma**: Internal database schema (how we store data)
- Database may have fields not exposed in API (audit logs, internal IDs)
- API may aggregate data from multiple tables

### Q: When would we add Zod to API routes?

**A**: Zod is already used in tests. Consider adding to API routes if:

- We need better validation error messages for users
- We want runtime validation of POST/PUT request bodies
- We need complex validation logic (cross-field validation)

**Example use case**:

```typescript
// Validate user registration in API route
import { RegisterSchema } from '@/lib/api-schemas';

export async function POST(request: NextRequest) {
  const body = await request.json();

  // Runtime validation with friendly errors
  const result = RegisterSchema.safeParse(body);
  if (!result.success) {
    return NextResponse.json({ error: result.error.format() }, { status: 400 });
  }

  // result.data is now type-safe and validated
  const user = await createUser(result.data);
  return NextResponse.json(user);
}
```

### Q: How do I add a new field?

**Workflow**:

1. Update `docs/api/openapi.yaml` with new field
2. Run `npm run api:generate:ts` (generates TypeScript types)
3. Run `npm run api:generate:swift` (generates Swift types)
4. Update Prisma schema if field needs database storage
5. Run `npx prisma migrate dev` (updates database)
6. Update API route to include new field in response
7. Run `npm run test:contract` (verifies compliance)
8. iOS app automatically gets new field via regenerated models

### Q: What if I change a field type?

**Breaking change workflow**:

1. Update OpenAPI spec (increment version if needed)
2. Regenerate types (TypeScript + Swift)
3. **CI will fail** if API responses don't match new spec
4. Update API routes to match new type
5. Update database schema if needed
6. iOS app needs recompile with new types

**Version management**:

- Maintain backward compatibility with older iOS clients
- Use API versioning (`/api/v1/books`, `/api/v2/books`) for major changes
